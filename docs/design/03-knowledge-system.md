# 03 — Knowledge System

Covers §12–§15 of the design brief.

---

## 12. Knowledge Representation

### 12.1 Requirements the format must satisfy

| # | Requirement | Why it constrains the choice |
| :-- | :-- | :-- |
| K1 | Readable by a human with no tooling | Contributors are engineers, not ontologists. Friction here kills the growth vector. |
| K2 | Readable by an agent with a file read | The consumption path must be `Read(path)` — no server, no index build, no query language. |
| K3 | Machine-queryable metadata | Relationships, thresholds, and categories must be extractable for indexing and validation. |
| K4 | Diffable and reviewable in a PR | Knowledge is contested; review is the quality mechanism. |
| K5 | Validatable in CI | Structure must be enforceable, or it degrades within 50 contributions. |
| K6 | Zero runtime dependencies | P7 (local-first) and P9 (dogfooding). |

### 12.2 Options compared

| Format | K1 | K2 | K3 | K4 | K5 | K6 | Verdict |
| :-- | :-: | :-: | :-: | :-: | :-: | :-: | :-- |
| **Markdown + YAML frontmatter** | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | **Chosen** |
| Pure Markdown | ✅ | ✅ | ❌ | ✅ | ⚠️ | ✅ | No structured relationships; indexing becomes regex archaeology |
| YAML/JSON only | ❌ | ⚠️ | ✅ | ⚠️ | ✅ | ✅ | Hostile to prose; nuance dies; contributors hate it |
| JSON-LD / RDF / OWL | ❌ | ⚠️ | ✅✅ | ❌ | ✅ | ✅ | Correct in theory, fatal in practice: ontology design becomes a prerequisite to contributing a paragraph about cache stampedes |
| Graph database (Neo4j) | ❌ | ❌ | ✅✅ | ❌ | ⚠️ | ❌ | Requires a server to read a fact. Violates K2 and P7 outright. |
| Vector database | ❌ | ⚠️ | ❌ | ❌ | ❌ | ❌ | Solves retrieval-at-scale, a problem OAB does not have at ~200 documents. Adds embedding drift, non-determinism, and a build step. |
| SQLite index | ✅* | ⚠️ | ✅ | ⚠️ | ✅ | ⚠️ | A *derived* index is defensible later; as the source of truth it fails K1/K4 |

### 12.3 Decision

**Markdown with YAML frontmatter, validated against JSON Schema, with a generated index.**

- **Source of truth:** `knowledge/<domain>/<slug>.md`. One file, one concept.
- **Structure:** YAML frontmatter conforming to `schemas/knowledge-unit.schema.json`.
- **Prose:** Markdown body with a fixed section skeleton so an agent can locate a part
  (e.g. "failure modes") without reading the whole file.
- **Derived artifacts** (generated by `tools/build_index.py`, committed, CI-verified fresh):
  - `knowledge/INDEX.md` — human-navigable map
  - `knowledge/index.json` — flat array of frontmatter + path, for programmatic selection
  - `knowledge/<domain>/README.md` — per-domain index used for progressive disclosure

The generated index is the only concession to machine efficiency, and it is *derived*, so it can be
deleted and rebuilt. If it ever disagrees with the source, the source wins.

**Revisit condition (recorded as ADR-0004):** move to a richer representation only when
`knowledge/` exceeds ~400 units **and** measured agent retrieval accuracy against the index drops
below 80% on the evaluation suite. Neither condition is close.

### 12.4 What must *not* be in a knowledge unit

- Verbatim copyrighted text. Summarise, then cite.
- Vendor recommendations disguised as facts.
- Undated performance numbers. Any concrete figure carries the hardware/version/date it was
  measured on, or it is a range with a stated basis.
- Advice without a condition. "Use a cache" is not knowledge; "use a cache when reads exceed X and
  the read:write ratio exceeds Y and staleness of Z seconds is acceptable" is.

## 13. Knowledge Unit Schema

### 13.1 Frontmatter schema (informal; normative version is `schemas/knowledge-unit.schema.json`)

| Field | Type | Required | Purpose |
| :-- | :-- | :-- | :-- |
| `id` | string, `^[a-z0-9]+(-[a-z0-9]+)*$` | ✅ | Stable identifier, unique repo-wide. Never changes; renames use `aliases`. |
| `title` | string | ✅ | Human title |
| `description` | string ≤ 300 chars | ✅ | One-sentence summary; used in indexes and agent selection |
| `category` | enum | ✅ | Top-level domain (matches directory) |
| `subcategory` | string | | Finer grouping |
| `tags` | string[] | | Free-form retrieval aids |
| `maturity` | enum: `draft` \| `reviewed` \| `stable` | ✅ | Trust signal. Agents prefer `stable`; `draft` is flagged as provisional in output. |
| `confidence` | enum: `high` \| `medium` \| `low` | ✅ | How settled the industry is on this. `low` implies genuine disagreement — record it. |
| `applies_at_stage` | string[] (`0`–`5`) | ✅ | Maturity stages where this is relevant. **The primary overengineering guard**: a stage-4 concept surfacing in a stage-1 design is a detectable defect. |
| `prerequisites` | id[] | | Concepts required to understand this one |
| `related` | id[] | | Peer concepts |
| `supersedes` / `superseded_by` | id[] | | Evolution of the knowledge itself |
| `trade_offs` | object[] | ✅ | `{ gains, costs, when_worth_it }` — structured, not prose |
| `failure_modes` | object[] | ✅ | `{ mode, symptom, detection, mitigation }` |
| `triggers` | object[] | | Measurable conditions that make this concept relevant — the link into the evolution framework |
| `anti_patterns` | string[] | | Named misuses |
| `complexity_cost` | integer 0–5 | ✅ | Operational burden if adopted. Feeds the Complexity Budget. |
| `references` | object[] | ✅ | `{ title, author?, url?, type, accessed }`. At least one. |
| `last_reviewed` | date | ✅ | Staleness signal; CI warns beyond 18 months |
| `aliases` | string[] | | Former ids, for stable linking |

### 13.2 Body skeleton

Fixed headings so an agent can jump to a section:

```markdown
## What it is
## When it applies          ← conditions and thresholds, not vibes
## When it does not apply   ← equally important; this is where overengineering is prevented
## How it works
## Trade-offs               ← prose expansion of the structured field
## Failure modes
## Measurement              ← what to instrument to know whether this is working
## Alternatives
## References
```

`## When it does not apply` is mandatory and is the section reviewers scrutinise hardest. A
knowledge base that only says when to use things is a machine for producing overengineering.

A complete worked example is in [§39](09-specifications.md#39-knowledge-schema-example).

## 14. Knowledge Graph

### 14.1 What the graph is (and is not)

The graph is **derived from frontmatter**, not stored separately. `prerequisites`, `related`,
`supersedes`, `category`, and `triggers` already form a directed labelled graph. `tools/build_index.py`
materialises it as:

- `knowledge/INDEX.md` — a nested, navigable tree by category with one-line descriptions
- `knowledge/index.json` — nodes + edges, for programmatic traversal
- `docs/knowledge-map/graph.mmd` — a Mermaid rendering per category, for the website

There is **no graph database**, no query engine, no server. Traversal at OAB's scale is
`json.load()` plus a dictionary lookup.

### 14.2 What the graph is *for*

Three concrete uses, all of which must exist or the graph is decoration:

1. **Agent retrieval.** "I am designing a cache. Which concepts must I consider?" →
   look up `caching`, follow `related` and `triggers`, read 3 files instead of 30.
2. **Contribution quality.** CI fails a PR that references a non-existent `id`, creates a
   `prerequisites` cycle, or adds an orphan node with no inbound or outbound edges. Orphans are
   almost always knowledge nobody will ever retrieve.
3. **Coverage visibility.** A generated report shows which categories are thin. This is how the
   project directs contributor effort honestly, rather than claiming completeness it lacks.

### 14.3 Illustrative shape

```
distributed-systems
├── consistency
│   ├── strong-consistency ──prereq──▶ linearizability
│   ├── eventual-consistency ──related──▶ conflict-resolution
│   └── causal-consistency
├── delivery-guarantees
│   ├── at-least-once ──related──▶ idempotency ──related──▶ deduplication
│   └── effectively-once ──prereq──▶ transactional-outbox
└── failure-modes
    ├── network-partition ──trigger──▶ circuit-breaker
    ├── thundering-herd ──related──▶ cache-stampede   (cross-domain edge into `caching`)
    └── retry-storm ──related──▶ exponential-backoff ──related──▶ jitter
```

Cross-domain edges (`thundering-herd` → `cache-stampede`) are the highest-value edges in the graph:
they are exactly the connections a specialist knows and a generalist misses.

### 14.4 Scope decision

**Graph generation is M2, not M1.** M1 ships the frontmatter fields (so the data exists from the
first unit) and a validator that checks referential integrity. Generating and rendering the graph
before there are ~40 units would produce an impressive-looking picture of almost nothing — which is
the diagram equivalent of overengineering, and §42 of the brief warns against exactly that.

## 15. Reasoning Framework

This is the heart of the project: how an agent gets from a vague request to a defensible decision.

### 15.1 The pipeline

```
  ┌──────────────┐
  │ 1 FRAME      │  What problem? What decision is actually being made?
  └──────┬───────┘  Output: problem statement + decision scope
         ▼
  ┌──────────────┐
  │ 2 GATHER     │  Repository evidence + targeted questions (max 5, high-impact only)
  └──────┬───────┘  Output: facts[], with source: observed | stated | assumed
         ▼
  ┌──────────────┐
  │ 3 ASSUME     │  Every gap becomes an explicit, labelled assumption with a confidence
  └──────┬───────┘  Output: assumptions[] — visible in the deliverable, never hidden
         ▼
  ┌──────────────┐
  │ 4 QUANTIFY   │  Run calculators. Deterministic arithmetic, ranges where inputs are uncertain
  └──────┬───────┘  Output: capacity-result artifacts (schema-valid)
         ▼
  ┌──────────────┐
  │ 5 CLASSIFY   │  Determine maturity stage (0–5) and Complexity Budget from team + money
  └──────┬───────┘  Output: stage, budget
         ▼
  ┌──────────────┐
  │ 6 RETRIEVE   │  Select knowledge units filtered by applies_at_stage ≤ stage
  └──────┬───────┘  Output: cited knowledge ids
         ▼
  ┌──────────────┐
  │ 7 OPTION     │  Generate ≥2 real options, always including the simplest viable one
  └──────┬───────┘  Output: options[] with complexity_cost and estimated £
         ▼
  ┌──────────────┐
  │ 8 CONSTRAIN  │  Apply the Complexity Budget. Over budget ⇒ reject or justify explicitly
  └──────┬───────┘  Output: budget check pass/fail per option
         ▼
  ┌──────────────┐
  │ 9 DECIDE     │  Choose. State rationale, trade-offs accepted, and confidence
  └──────┬───────┘  Output: decision + rationale
         ▼
  ┌──────────────┐
  │10 TRIGGER    │  Define measurable revisit conditions for every significant choice
  └──────┬───────┘  Output: triggers[] (schema-valid)
         ▼
  ┌──────────────┐
  │11 RECORD     │  Emit ADR + structured artifact (the thing evaluations assert against)
  └──────────────┘
```

Steps 4, 5, 8 and 10 are what distinguish OAB from a well-written prompt. They are the steps a
model will skip unless a procedure forces them, and they are the steps that produce
proportionality.

### 15.2 Hard rules the agent must obey

| Rule | Enforcement |
| :-- | :-- |
| **R-A** No recommendation without a number, or an explicit "unquantified — provisional" label | Evaluation assertion |
| **R-B** Every assumption appears in the output, with confidence | Schema requires `assumptions[]` non-empty |
| **R-C** Every option set includes the simplest viable option, even when rejected | Evaluation assertion |
| **R-D** Every significant decision carries ≥1 measurable trigger | Schema + assertion |
| **R-E** Never introduce a component absent from any generated option | Review of artifact vs. narrative |
| **R-F** Stage-N system may not use stage-(N+2) machinery without an explicit, written override | `applies_at_stage` filter + assertion |
| **R-G** State confidence honestly; `low` confidence must recommend measurement before commitment | Assertion |
| **R-H** Cite knowledge unit ids used | Artifact field `knowledge_used[]` |

### 15.3 Traceable reasoning as an artifact

Every OAB deliverable carries a machine-readable reasoning trace alongside the prose. This is what
makes §23's deterministic evaluation possible and what makes the reasoning contestable:

```yaml
# reasoning trace — conforms to schemas/reasoning-trace.schema.json
decision: "Primary datastore"
stage: 1
complexity_budget: { available: 4, spent: 4 }
inputs:
  - { fact: "peak RPS", value: 0.28, source: calculated, confidence: medium }
  - { fact: "team size", value: 2, source: stated, confidence: high }
  - { fact: "budget GBP/month", value: 50, source: stated, confidence: high }
assumptions:
  - { text: "30% of registered users are daily active", confidence: low, impact: "±3× on RPS" }
  - { text: "average record size 2 KB", confidence: medium, impact: "±2× on storage" }
knowledge_used: [relational-vs-document, managed-vs-self-hosted-database, connection-pooling]
options:
  - { id: managed-postgres, complexity_cost: 1, monthly_gbp: 15, verdict: selected }
  - { id: sqlite-on-volume,  complexity_cost: 0, monthly_gbp: 0,  verdict: rejected,
      reason: "no managed backup/PITR; restore is manual and untested" }
  - { id: postgres-plus-redis, complexity_cost: 2, monthly_gbp: 25, verdict: rejected,
      reason: "0.28 peak RPS — no measured read pressure to relieve" }
confidence: high
triggers: [db-cpu-sustained-70, p95-query-latency-slo-breach, storage-60pct-plan]
```

### 15.4 Where the model is allowed to be a model

Deliberate separation of concerns:

| Deterministic (code / schema / assertion) | Model judgement |
| :-- | :-- |
| Arithmetic and unit conversion | Framing the problem |
| Stage classification from stated inputs | Deciding which questions actually matter |
| Complexity budget computation | Weighing incommensurable trade-offs |
| `applies_at_stage` filtering | Reading a repository and inferring intent |
| Schema validation of artifacts | Writing prose a human wants to read |
| Trigger threshold arithmetic | Recognising the unstated constraint |

The model is never asked to multiply, and code is never asked to have taste.
