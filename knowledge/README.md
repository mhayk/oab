# OAB Knowledge Base

Architecture knowledge as executable instructions to a reasoning agent, not as documentation.

One file, one concept. Each unit records what a thing is, when it applies, **when it does not**,
its trade-offs, its failure modes, and how to measure whether it is working.

## Navigating

- **[INDEX.md](INDEX.md)** — the full map *(generated once units exist)*
- **`<domain>/README.md`** — per-domain index; this is the progressive-disclosure entry point an
  agent scans to pick precisely the files a decision depends on
- **`index.json`** — flat records for programmatic selection

Indexes are generated by `tools/build_index.py` from frontmatter and are CI-checked for staleness.
Never edit them by hand.

Files whose name begins with `_` are **reference material, not knowledge units** — price tables and
similar data that carry a `Checked:` date rather than the unit schema. They are excluded from
validation and indexing.

## Domains

| Domain | Covers |
| :-- | :-- |
| `fundamentals/` | The concepts every other domain leans on, including how architecture is judged proportional to its problem |
| `databases/` | Choosing and operating datastores by workload characteristics rather than preference |
| `caching/` | When a cache earns its place, and — more often — when it does not |
| `messaging/` | Asynchronous processing, weighted toward the simple options that are almost always sufficient |
| `reliability/` | Failure modes, and the mechanisms that address them, with their parameters |
| `cost/` | Infrastructure cost, and the operational cost no cloud calculator models |

Six domains, deliberately. Forty deep units beat two hundred stubs: breadth looks like progress and
produces nothing usable. More domains arrive in M2, after this quality bar is established.

## Reading a unit

Every unit has the same body skeleton, so an agent can jump to a section without reading the file:

```
## What it is
## When it applies          ← conditions and thresholds, not adjectives
## When it does not apply   ← mandatory; this is where overengineering is prevented
## How it works
## Trade-offs
## Failure modes
## Measurement              ← what to instrument to know it is working
## Alternatives
## References
```

Frontmatter carries the machine-readable part: `applies_at_stage` (the overengineering guard),
`complexity_cost` (feeds the complexity budget), structured `trade_offs` and `failure_modes`,
measurable `triggers`, and attributed `references`.
