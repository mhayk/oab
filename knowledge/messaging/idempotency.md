## What it is

An operation is idempotent when applying it twice has the same effect as applying it once. Some
operations are naturally idempotent (`SET status = 'paid'`); most writes are not (`INSERT order`,
charge a card, send an email).

The general mechanism is an **idempotency key**: the client generates a unique key per intent, the
server records it with the result, and a repeat of the same key returns the stored result instead of
re-applying the effect.

## When it applies

Wherever a retry is possible — which is wherever there is a timeout, a queue, or a network. The
decisive case is the **ambiguous timeout**: a payment request that timed out may or may not have
succeeded, and without a key there is no safe action. Retrying may double-charge; not retrying may
lose the order.

Also required for any at-least-once delivery system, which is nearly all of them.

## When it does not apply

**Naturally idempotent operations.** Setting a field to an absolute value, deleting by id, or an
upsert on a natural key need nothing extra. Do not add machinery for them.

**Reads.** Idempotent by definition.

**Where duplicates are genuinely harmless** — an analytics event that is counted twice in a
dashboard nobody bills from. Say so explicitly rather than leaving it unexamined.

**When the operation cannot be retried at all.** If the caller gives up permanently on failure, an
idempotency key is unused machinery.

## How it works

The key must be written **in the same transaction as the effect**. Writing it afterwards leaves a
window where a crash produces a duplicate — which is exactly the failure the key was meant to
prevent.

The key is generated by the **client**, per intent, not derived from the payload. Deriving it from
the data collapses two legitimately identical requests: a user genuinely ordering the same item
twice cannot.

Keys need a retention window longer than the maximum retry window — typically 24 hours to a few
days — then deletion, or the table grows without bound.

## Trade-offs

A key to generate, store, and expire. Storage grows with request volume. In exchange, retries become
safe and ambiguous timeouts become resolvable, which is what makes every other resilience mechanism
usable.

## Failure modes

Storing the key after the effect is the subtle one, because it works in testing and fails only on a
crash at exactly the wrong moment — which, at volume, happens.

## Measurement

Track idempotent replay rate — requests served from a stored key. A rising rate indicates upstream
retries and is an early signal of a degrading dependency.

Track idempotency table size and confirm expiry is running.

## Alternatives

| Approach | When to prefer |
| :-- | :-- |
| Naturally idempotent design | Always preferred where the operation allows it |
| Client-generated idempotency key | Non-idempotent operations that can be retried |
| Deduplication window on a consumer | Message consumers where the producer cannot supply a key |
| Unique constraint on a natural key | Where one exists; the database enforces it for free |
